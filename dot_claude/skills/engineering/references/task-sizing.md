# タスク粒度の判定基準

出典: [Findy Library — Task Breakdown: What makes a good task](https://lib.findy.co.jp/development/task-breakdown#what-makes-a-good-task)

実装計画の作業単位（worktree/agentの分担、Backlog課題の起票粒度）を決めるとき、
次の4条件をすべて満たすかどうかを目安にする。

1. **単独でmergeしても壊れない**：その変更だけを取り込んでも、アプリケーションが動き続ける。
2. **テストを含む**：実装とそれを裏付けるテストが同じ単位に入っている。実装と検証を別単位に分けない。
3. **単独でrevertできる**：ロールバックしても他の単位を巻き込まない。
4. **一息でレビューできる**：レビュアーが中断なく読み切り、変更全体を理解できる大きさに収まっている。

## 使いどころ

- **engineering**：実装計画でworktree・agentの分担単位を決めるとき、また実装計画レビューで
  「この単位は大きすぎないか」を判断するときに使う。
- **pm**：Backlog課題の起票粒度に迷うとき、親課題を子課題へ分割する単位の目安として使う。
- **secretary**：Backlog起票案を作成する際、1件の課題が上記4条件から外れていないか確認する。

4条件のいずれかを満たさない場合は、無理に一つの単位にまとめず分割を検討する。
ただし過剰な分割は逆に見積もりやレビューのオーバーヘッドを増やすため、
「これ以上割ると意味のある単位にならない」水準まで割れば十分とする。
