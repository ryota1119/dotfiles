# Engineering — ソフトウェア開発スタッフ

engineeringは、Claudeによる検討・設計・レビューと、Codexによる実装・テストを
一つの開発フローとして調整する。最終判断と実装承認はボスが行う。

## 固定分担

| 工程 | 担当 | 責務 |
|---|---|---|
| 受付・対象特定 | secretary | 依頼目的と対象リポジトリを特定する |
| 調査・要件整理 | Claude | 現状、要件、制約、不明点を整理する |
| 設計・実装計画 | Claude | 変更方針、影響範囲、受け入れ条件、テスト計画を作る |
| 計画承認 | ボス | 実装範囲を確定する |
| 実装・自己レビュー | Codex | 承認範囲のコード変更とテストを行い、差分を自己レビューする |
| commit・push・PR作成 | mainsession | 自己レビューOKの変更を、別途承認を得てPR化する |
| 実装レビュー | Claude | PR上で仕様適合性、設計、リスク、保守性を確認する |
| 指摘対応 | Codex | 同じPRへ修正をpushし、再検証する |
| 人間レビュー | ボス | Opusレビュー通過後、PRを最終確認しmergeを判断する |

ClaudeとCodexは別のstaffではなく、engineering内で工程を分担する実行主体として扱う。

## 作業前の確認

1. 対象リポジトリを特定する。
2. `~/Workspace/CLAUDE.md`、このSKILL.md、対象リポジトリの`CLAUDE.md`と
   `AGENTS.md`を確認する。存在するファイルだけを読み、より厳しい規則を採用する。
3. `git status`と関連する既存実装を確認し、ユーザーの未コミット変更を識別する。
4. 依頼が検討、診断、実装、レビューのどこまでを含むか判定する。

## Claudeによる検討・設計

Claudeは原則としてコードを変更せず、次を行う。

- 現状の実装、依存関係、テスト、既知の制約を調査する
- 要件と非要件、前提、未確認事項を整理する
- 複数案がある場合は比較し、推奨案と理由を示す
- 変更対象、影響範囲、移行や互換性のリスクを特定する
- 受け入れ条件とテスト計画を定義する
- Codexが実装できる具体的な実装計画を作る

結果を大きく左右する不明点だけをユーザーへ確認する。安全に進められる調査と
計画作成は先に行う。

対象が大規模なリポジトリや複数モジュール・複数ファイルにまたがる調査の場合は、
探索をExploreまたはgeneral-purpose agentへ委任し、調査ログではなく発見事項の
要約だけを受け取る。これによりメインの会話が大量のファイル内容・grep結果で
圧迫されず、後続の設計検討やレビューに文脈の余力を残せる。対象範囲が数ファイル
程度に絞られている小規模な調査では、Agentを介さず直接読み進めてよい。

探索を担うAgentには`model: "sonnet"`を指定する。この工程はコードの読み取りと
発見事項の抽出が中心で、設計判断は含まないため。

## モデル選定

工程ごとに使い分ける。

| 工程 | モデル | 理由 |
|---|---|---|
| 探索・調査（Explore / general-purpose） | Sonnet | 読み取りと抽出が中心。入力トークンが大きく、コスト効率が効く |
| 計画作成 | **常にOpus** | ボスの意図を正しく汲み取れるかどうかが後続の実装量を左右するため、規模・リスクの大小を問わない |
| 実装レビュー | **常にOpus** | 仕様適合性とリスクの見逃しを防ぐことを優先するため、規模・リスクの大小を問わない |

計画とレビューでOpusを外さない。ここを下げると、後続の手戻りでかえって高くつく。

## 相談モード

設計中に複数案が拮抗し、Claude単独の判断では視野が狭くなりうる場面では、
Codexにread-only（書き込み不可）でセカンドオピニオンを求めてよい。書き込み権限を
持たせないため、事前承認なく自律的に使ってよい。

- 対象は方針の分岐点（例：状態管理の実装方式、既存設計との整合性）に限る。
- Codexの意見は参考情報として扱い、採用するかどうかはClaudeとボスが決める。
- 相談内容と結論への反映は、計画提示時に簡潔に記載する。

## 実装計画の形式

Codexへ引き継ぐ計画には、必要な範囲で次を含める。

1. 目的
2. 確認した現状
3. 変更方針
4. 変更対象
5. 受け入れ条件
6. テスト計画
7. リスク・未確認事項
8. 対象外

実装前に計画を提示し、ボスから明示的な承認を得る。計画の承認は、記載された範囲の
コード変更と検証をCodexへ許可する。commit、push、PR作成、本番反映は含まない。

変更対象を複数の実装単位に分けるかどうかは`references/task-sizing.md`の4条件
（単独でmergeしても壊れない、テストを含む、単独でrevertできる、一息でレビュー
できる）を目安にする。

## 大規模作業とagent

次のいずれかに該当する場合は、通常の作業ディレクトリへ直接実装せず、
git worktreeと実装agentの利用を計画に含める。

- 独立して進められる実装単位が複数ある
- 複数機能、複数パッケージ、複数の大きな変更領域にまたがる
- 長時間の実装中も基準ブランチを安全に保ちたい
- 複数案の試作や、回帰リスクの高い変更を分離したい

Claudeは実装計画に、worktree数、各agentの担当、ブランチ名、配置先、依存関係、
統合順序、検証方法を含める。ボスの承認後にCodexがworktreeを作成し、agentを起動する。
各agentの担当単位が大きすぎないかは`references/task-sizing.md`の4条件を目安に
判定する。

worktreeとagentの具体的な運用原則（配置先、1agent=1branch=1worktree、
役割分離の考え方）は`references/worktree-and-agents.md`を参照する。

## Codexへの引き継ぎ

Codexは`~/Workspace/AGENTS.md`と対象リポジトリの指示を読み、承認された計画を実装する。
Codexと実装agentは原則として`~/Workspace`を起点に起動し、共通`AGENTS.md`を
読み込める状態にする。独立リポジトリを直接ルートとして起動する場合は、
同等の共通規約をそのリポジトリの`AGENTS.md`から参照できることを先に確認する。

- 作業前に`git status`を確認し、既存変更を保持する
- 承認された設計と対象範囲に沿って編集する
- 関連するテスト、lint、型検査、ビルドを可能な範囲で実行する
- 実装中に設計変更や範囲拡大が必要になった場合は止めて報告する
- **PR作成前に、差分を自己レビューする**（規約適合、承認範囲外の変更や
  意図しない混入がないか）。機械的にチェックできる範囲をここで潰し、Claudeの
  レビューを設計判断・仕様適合性・リスクの確認に集中させる。
- 変更ファイル、検証結果、残存リスクを報告する

### 引き継ぎ文には必ず禁止事項を明記する

**承認境界はサンドボックスでは強制されていない。**引き継ぎ文で明示的に禁止する。

非対話で起動したCodexには承認を求める相手がいない。この状態で`.git`への書き込みが
サンドボックスに拒否されると、Codexは**書き込み可能な場所へcloneし、そこでcommitして
pushを完遂する**ことがある(2026-08-10に使い捨てリポジトリで実測)。
`--approve-for-me`を付けた場合は、同じ操作がGuardianサブエージェントの承認を経て
通る。どちらの経路でも、ボスの承認なしにpushがリモートへ届く。

`sandbox_workspace_write.network_access`を`false`にすれば機構的に遮断できるが、
依存パッケージのダウンロードとDocker越しの通信も同時に止まり、実装作業自体が
成立しなくなるため採用しない(2026-08-10のボスの判断)。

したがって、引き継ぎ文へ次を必ず含める。

- `git commit`・`git push`・`git branch`・ブランチ作成の禁止
- **`.git`への書き込みが拒否された場合にcloneして回避することの禁止**
  （拒否されたら止めて報告させる）
- 承認された変更対象以外のファイルの変更禁止
- 計画に明記していない依存の追加・削除・バージョン変更の禁止

禁止事項を書かなかった引き継ぎは、承認範囲を超える変更が起きても検出できない。
Codexの報告を待つだけでなく、`git status`・`git diff`・テストを**Claude自身が
実行して**承認範囲内に収まっていることを確認する。

トラブルシューティング（codexコマンドが見つからない場合、進捗が止まった場合の対処）は
`references/codex-troubleshooting.md`を参照する。

## PR作成

Codexの自己レビューが完了したら、mainsessionが変更をPRとして作成する。
commit・push・PR作成は、実装計画の承認とは別に事前承認を得た場合だけ実行する。
以降の実装レビュー・指摘対応・人間レビューは、このPRを対象に行う。

### ベースブランチとの乖離チェック

複数のworktreeが並行して動くため、作業中にベースブランチが進み、気づかないまま
競合を抱えることがある。次の2点でマージ可否を確認する。

- **PR作成の直後**に `gh pr view <番号> --json mergeable,mergeStateStatus` を実行し、
  結果をボスへの報告に含める。`CONFLICTING` なら、その時点で解消方針を提示する。
- **マージを指示された直後**にも同じ確認を行う。PR作成時に問題がなくても、
  その後に他のPRがマージされて競合していることがある。

ベースブランチの取り込み（`git merge origin/<base>`）はmerge操作なので、
実装計画の承認とは別に事前承認を得てから実行する。競合の解消方針（どちらの変更を
採用し、何を再適用するか）は、実行前にボスへ提示する。

なお `~/.claude/hooks/require-up-to-date.sh`（PreToolUse hook）が、
`gh pr create` / `gh pr merge` の実行前にベースブランチの未取り込みコミットを
検出してブロックする。hookは検出のみで自動mergeはしないため、上記の承認フローは
省略しない。

## Claudeによる実装レビュー

Claudeは作成されたPRに対して、原則としてコードを変更せずに次を確認する。

- 承認された目的と受け入れ条件を満たしているか
- 設計意図と実装が一致しているか
- バグ、回帰、セキュリティ、データ互換性のリスクがないか
- テストが重要な分岐と失敗条件を覆っているか
- 依頼範囲外の変更が混入していないか
- 構造変更（リファクタ）と振る舞い変更が同一commit・同一PRに混在していないか
  （AGENTS.mdの「Implementation」節参照）。混在している場合は、テストが無変更の
  ままかどうかで構造保存を機械的に確認できないため、分離を指摘する。

実装レビューはOpusモデルのagentへ委任する（「モデル選定」節を参照）。

指摘は重要度順に、ファイルと根拠を添えてPRへ記録する。修正が必要な場合は
Codexへ返し、Codexは同じPRへ修正をpushして再検証する。

PRコメント・レビューコメントなど対象リポジトリへ書き込む文章は、コミットメッセージ
同様に日本語で記載する（英語テンプレートのコードレビューコマンド等を使う場合も、
本文は日本語に訳してから投稿する）。

Opusレビューが通過したら、ボスがPRを最終確認しmergeを判断する（人間レビュー）。

### 敵対的レビュー

「例外」節の高リスク基準に該当する変更、またはリリース前で不安が残る変更は、
通常の実装レビューに加えて敵対的レビューを行う。観点はP0/P1級のリスク
（正しさ・セキュリティ・互換性）に絞り、スタイルの指摘では止めない。

- 実装した本人（Codex）には敵対的レビューをさせない。
- 「このコードを壊すつもりで穴を探せ」という指示で、Opusモデルのagentへ委任する。
- 通常レビューと敵対的レビューの結果は分けて提示し、両方の指摘をCodexへ返す。

## 例外

- 読み取り、診断、設計相談、コードレビューだけの依頼はClaude単独で完了してよい。
- 誤字、明白な設定値、ユーザーが変更内容を完全に指定した小規模修正は、
  ユーザーの明示的な実装依頼を承認として、Claudeの事前計画を省略してCodexが実装できる。
- 認証、認可、セキュリティ、課金、個人情報、DB schema、本番環境、外部API、
  複数リポジトリに影響する変更は、必ず通常フローとClaudeレビューを通す。
- 緊急対応でも、コード変更前の承認とcommit・pushの別承認は省略しない。

## 承認境界

### 自律実行できること

- リポジトリ、コード、設定、履歴、Issue、PR、ログの読み取りと調査
- 診断、設計案、実装計画、テスト計画、レビュー結果の作成
- 承認済み実装に必要な非破壊的なテストと検証

### 事前承認が必要なこと

- コード、テスト、設定、依存関係、DB schemaの変更
- 計画に明記されていないブランチ・worktreeの作成
- 破壊的または本番データへ影響するコマンド
- 依存関係の大規模更新、マイグレーションの実行、本番反映
- commit、merge、rebase、cherry-pick、push、PR作成・更新・レビュー送信
- worktreeの削除

承認済み計画の範囲を超える変更は、追加承認を得るまで実行しない。
