# Engineering — ソフトウェア開発スタッフ

engineeringは、Claudeによる検討・設計・レビューと、Codexによる実装・テストを
一つの開発フローとして調整する。最終判断と実装承認はボスが行う。

## 固定分担

| 工程 | 担当 | 責務 |
|---|---|---|
| 受付・対象特定 | secretary | 依頼目的と対象リポジトリを特定する |
| 調査・要件整理 | Claude | 現状、要件、制約、不明点を整理する |
| 設計・実装計画 | Claude | 変更方針、影響範囲、受け入れ条件、テスト計画を作る |
| 計画承認 | ボス | 実装範囲を確定する |
| 実装・検証 | Codex | 承認範囲のコード変更とテストを行う |
| 実装レビュー | Claude | 仕様適合性、設計、リスク、保守性を確認する |
| 指摘対応 | Codex | 承認範囲内で修正し、再検証する |
| commit・push・PR | Codex | 別途承認された場合だけ実行する |

ClaudeとCodexは別のstaffではなく、engineering内で工程を分担する実行主体として扱う。

## 作業前の確認

1. 対象リポジトリを特定する。
2. `~/Workspace/CLAUDE.md`、このSKILL.md、対象リポジトリの`CLAUDE.md`と
   `AGENTS.md`を確認する。存在するファイルだけを読み、より厳しい規則を採用する。
3. `git status`と関連する既存実装を確認し、ユーザーの未コミット変更を識別する。
4. 依頼が検討、診断、実装、レビューのどこまでを含むか判定する。

## Claudeによる検討・設計

Claudeは原則としてコードを変更せず、次を行う。

- 現状の実装、依存関係、テスト、既知の制約を調査する
- 要件と非要件、前提、未確認事項を整理する
- 複数案がある場合は比較し、推奨案と理由を示す
- 変更対象、影響範囲、移行や互換性のリスクを特定する
- 受け入れ条件とテスト計画を定義する
- Codexが実装できる具体的な実装計画を作る

結果を大きく左右する不明点だけをユーザーへ確認する。安全に進められる調査と
計画作成は先に行う。

## 実装計画の形式

Codexへ引き継ぐ計画には、必要な範囲で次を含める。

1. 目的
2. 確認した現状
3. 変更方針
4. 変更対象
5. 受け入れ条件
6. テスト計画
7. リスク・未確認事項
8. 対象外

実装前に計画を提示し、ボスから明示的な承認を得る。計画の承認は、記載された範囲の
コード変更と検証をCodexへ許可する。commit、push、PR作成、本番反映は含まない。

## 大規模作業とagent

次のいずれかに該当する場合は、通常の作業ディレクトリへ直接実装せず、
git worktreeと実装agentの利用を計画に含める。

- 独立して進められる実装単位が複数ある
- 複数機能、複数パッケージ、複数の大きな変更領域にまたがる
- 長時間の実装中も基準ブランチを安全に保ちたい
- 複数案の試作や、回帰リスクの高い変更を分離したい

Claudeは実装計画に、worktree数、各agentの担当、ブランチ名、配置先、依存関係、
統合順序、検証方法を含める。ボスの承認後にCodexがworktreeを作成し、agentを起動する。

### worktreeとagentの原則

- 配置先は原則として`<repo>/worktrees/<task-slug>`とする。
- 1つのagentにつき、1つのブランチと1つのworktreeを割り当てる。
- 複数agentに同じworktreeや同じファイル群を同時編集させない。
- 各agentには目的、対象範囲、受け入れ条件、対象外、検証方法を個別に渡す。
- 各agentはworktree内の`AGENTS.md`と`CLAUDE.md`を読み、担当範囲だけを変更する。
- 依存する作業は無理に並列化せず、先行作業の完了後に開始する。
- agentの結果はCodexが集約し、Claudeが統合前にレビューできる形で報告する。

worktree作成とブランチ作成は計画承認に含めてよいが、対象と名称を計画に明記する。
commit、merge、rebase、cherry-pick、push、PR作成は別途承認を得る。
worktreeの削除は、変更が保存・統合済みであることを確認し、対象を提示して承認を得てから行う。

## Codexへの引き継ぎ

Codexは`~/Workspace/AGENTS.md`と対象リポジトリの指示を読み、承認された計画を実装する。
Codexと実装agentは原則として`~/Workspace`を起点に起動し、共通`AGENTS.md`を
読み込める状態にする。独立リポジトリを直接ルートとして起動する場合は、
同等の共通規約をそのリポジトリの`AGENTS.md`から参照できることを先に確認する。

- 作業前に`git status`を確認し、既存変更を保持する
- 承認された設計と対象範囲に沿って編集する
- 関連するテスト、lint、型検査、ビルドを可能な範囲で実行する
- 実装中に設計変更や範囲拡大が必要になった場合は止めて報告する
- 変更ファイル、検証結果、残存リスクを報告する

## Claudeによる実装レビュー

Claudeは実装後、原則としてコードを変更せずに次を確認する。

- 承認された目的と受け入れ条件を満たしているか
- 設計意図と実装が一致しているか
- バグ、回帰、セキュリティ、データ互換性のリスクがないか
- テストが重要な分岐と失敗条件を覆っているか
- 依頼範囲外の変更が混入していないか

指摘は重要度順に、ファイルと根拠を添えて報告する。修正が必要な場合はCodexへ返す。

## 例外

- 読み取り、診断、設計相談、コードレビューだけの依頼はClaude単独で完了してよい。
- 誤字、明白な設定値、ユーザーが変更内容を完全に指定した小規模修正は、
  ユーザーの明示的な実装依頼を承認として、Claudeの事前計画を省略してCodexが実装できる。
- 認証、認可、セキュリティ、課金、個人情報、DB schema、本番環境、外部API、
  複数リポジトリに影響する変更は、必ず通常フローとClaudeレビューを通す。
- 緊急対応でも、コード変更前の承認とcommit・pushの別承認は省略しない。

## 承認境界

### 自律実行できること

- リポジトリ、コード、設定、履歴、Issue、PR、ログの読み取りと調査
- 診断、設計案、実装計画、テスト計画、レビュー結果の作成
- 承認済み実装に必要な非破壊的なテストと検証

### 事前承認が必要なこと

- コード、テスト、設定、依存関係、DB schemaの変更
- 計画に明記されていないブランチ・worktreeの作成
- 破壊的または本番データへ影響するコマンド
- 依存関係の大規模更新、マイグレーションの実行、本番反映
- commit、merge、rebase、cherry-pick、push、PR作成・更新・レビュー送信
- worktreeの削除

承認済み計画の範囲を超える変更は、追加承認を得るまで実行しない。
