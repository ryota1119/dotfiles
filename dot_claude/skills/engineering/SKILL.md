# Engineering - ソフトウェア開発スタッフ

engineeringは、設計、実装、レビューを一つの開発フローとして調整する。最終判断と
実装承認はユーザーが行う。

## 役割分担

| 工程 | 担当 | 責務 |
|---|---|---|
| 受付・対象特定 | 窓口担当 | 依頼目的と対象リポジトリを特定する |
| 調査・要件整理 | 設計担当 | 現状、要件、制約、不明点を整理する |
| 設計・実装計画 | 設計担当 | 変更方針、影響範囲、受け入れ条件、テスト計画を作る |
| 計画承認 | ユーザー | 実装範囲を確定する |
| 実装・自己レビュー | 実装担当 | 承認範囲の変更、テスト、差分の自己レビューを行う |
| commit・push・PR作成 | メインセッション | 別途承認を得た変更だけをPR化する |
| 実装レビュー | レビュー担当 | 仕様適合性、設計、リスク、保守性を確認する |
| 独立レビュー | 別のレビュー担当 | 高リスク変更を読み取り専用で検証する |
| 人間レビュー | ユーザー | PRを最終確認し、統合を判断する |

実行環境の名称や提供者ではなく、この役割と責務で分担する。

## 実行主体の割り当て

工程ごとの実行主体は次を既定とする。model・effortは各Agent定義の
frontmatterで宣言し、この表では参照しない。

| 工程 | 実行主体 |
|---|---|
| 受付・対象特定 | メインセッション |
| 調査（大規模・複数モジュール） | `repo-explorer` |
| 調査（小規模） | メインセッション |
| 設計・実装計画 | メインセッション |
| 実装・自己レビュー | `impl-worker` |
| 実装レビュー | `code-reviewer` |
| 独立・敵対的レビュー | Codex（`/codex:adversarial-review`。高リスク変更のみ） |
| commit・push・PR作成 | メインセッション |

該当するAgentが利用できない実行環境では、メインセッションが同じ責務と制約のまま
直接実行する。Agentの有無で成果物の要件を下げない。

## 作業前の確認

1. 対象リポジトリを特定する。
2. 共通規約、このSKILL.md、対象リポジトリの指示ファイルを確認し、存在するもののうち
   より厳しい規則を採用する。
3. `git status`と関連実装を確認し、ユーザーの未コミット変更を識別する。
4. 依頼が検討、診断、実装、レビューのどこまでを含むか判定する。

## 調査と設計

設計担当は原則としてコードを変更せず、現状、依存関係、テスト、制約を調査し、要件、
非要件、リスク、受け入れ条件、テスト計画を整理する。複数案がある場合は比較し、推奨案と
理由を示す。結果を大きく左右する不明点だけをユーザーへ確認する。

大規模なリポジトリや複数モジュールにまたがる探索では、専用の読み取りAgent
`repo-explorer`へ委任する。委任先は発見事項の要約だけを返し、設計判断は行わない。
小規模な調査は直接読み進めてよい。

設計と実装計画はメインセッションで行う。全体文脈とユーザーとの対話が必要なため、
この工程をAgentへ委任しない。

設計上の分岐点では、別の読み取り専用レビュー担当へセカンドオピニオンを求めてよい。
意見は参考情報として扱い、採用は設計担当とユーザーが判断する。

## 実装計画と承認

実装計画には、必要な範囲で目的、確認した現状、変更方針、変更対象、受け入れ条件、
テスト計画、リスク・未確認事項、対象外を含める。受け入れ条件は「入力から期待結果」まで
具体化する。

実装前に計画を提示し、ユーザーから明示的な承認を得る。計画承認は記載範囲の変更と検証を
許可するだけであり、commit、push、PR作成、本番反映は含まない。

変更単位の分割は`references/task-sizing.md`の4条件を目安にする。

## 大規模作業とworktree

独立した実装単位が複数ある、複数の大きな変更領域にまたがる、基準ブランチを保護したい、
または回帰リスクを分離したい場合は、worktreeと実装Agentの利用を計画に含める。

計画にはworktree数、各担当の対象、ブランチ名、配置先、依存関係、統合順序、検証方法を
含める。ユーザー承認後に作成し、具体的な安全要件は
`references/worktree-and-agents.md`を参照する。

## 実装と自己レビュー

実装は`impl-worker`へ委任する。実装担当は承認済み計画と対象リポジトリの規約に従い、
既存変更を保持して実装する。

- 作業前に`git status`を確認する
- 承認された設計と対象範囲に沿って編集する
- 関連するテスト、lint、型検査、ビルドを可能な範囲で実行する
- 設計変更や範囲拡大が必要になった場合は止めて報告する
- PR作成前に差分を自己レビューし、承認範囲外の混入がないか確認する
- 変更ファイル、検証結果、残存リスクを報告する

引き継ぎ文には、`git commit`、`git push`、`git branch`、ブランチ作成の禁止、`.git`への
書き込み拒否をcloneで回避しないこと、承認対象外の変更禁止、未承認の依存変更禁止を
明記する。メインセッションは報告だけに依存せず、`git status`、`git diff`、テストを
実行して承認範囲内であることを確認する。

## PRとブランチ乖離確認

commit、push、PR作成・更新・レビュー送信は、実装計画の承認とは別に事前承認を得た場合だけ
実行する。

ベースブランチとの乖離確認は必須の手動確認とする。PR作成直後とマージ指示直後に
`gh pr view <番号> --json mergeable,mergeStateStatus`を実行し、結果をユーザーへ報告する。
競合している場合は、解消方針を提示してから進める。ベースブランチの取り込みも別途承認を
得る。実行環境でhookが利用可能な場合は補助的に利用できるが、この手動確認と承認フローを
置き換えない。

## 実装レビュー

レビューは三層で行う。層1と層2は常時、層3は高リスク変更のみとする。

| 層 | 実行主体 | 観点 |
|---|---|---|
| 1. 自己レビュー | 実装担当（`impl-worker`） | 承認範囲外の混入、差分の整合 |
| 2. 実装レビュー | `code-reviewer`（読み取り専用） | 受け入れ条件、バグ、回帰、セキュリティ、互換性、テスト網羅性 |
| 3. 独立・敵対的レビュー | Codex（別モデル、読み取り専用） | 設計前提の妥当性、代替案、実運用での破綻 |

層2のレビュー担当は原則として変更せず、指摘は重要度順にファイルと根拠を添える。

層3は、実装したモデルとは別のモデルで検証することを目的とする。同じモデルが書いて
同じモデルが読むと見落としが相関するため、層2の強化では代替できない。結果は層2とは
分けて提示する。

### 層3の発動条件（高リスク変更）

次のいずれかに該当する場合に実施する。

- 公開APIの変更、DB schemaの変更、データ移行・削除処理
- 認証・認可、テナント分離、権限境界に触れる変更
- 課金・決済に関わる変更
- `references/task-sizing.md`の4条件を超える規模の変更

### 層3の実行方法

実行環境によって経路が変わる。実行時に利用可能なコマンドを確認して選ぶ。

**Claude Code上で、codexプラグインが利用できる場合**

`/codex:adversarial-review`を使う。専用の敵対レビュープロンプトと構造化出力スキーマ
（severity、`path`、行範囲、confidence、推奨修正を必須化）を備えており、手書きの
プロンプトより所見の具体性と再現性が高い。

このコマンドは`disable-model-invocation`のためメインセッションから自律実行できない。
層3が必要と判断した時点で、ユーザーへ次の実行を促す。

```
/codex:adversarial-review --background
```

重点観点があれば、フラグの後に焦点テキストを添えるよう伝える。差分ではなく実装計画や
設計そのものをレビューしたい場合、または対象がstaged/unstaged片側に限られる場合は、
このコマンドでは狙えないため`/codex:rescue`を使う。

**Codex単独環境の場合**

`codex review`を使う。レビュー用モデルは`~/.codex/config.toml`の`review_model`で
実装用モデルと別に設定してあり、新規セッションで実行される。

```
codex review
```

この場合、実装とレビューが同一ベンダーのモデルになるため、層3が本来狙う「見落としの
非相関」は部分的にしか得られない。得られるのは別モデルであることと、自分の推論過程を
引き継がない新規セッションであることの2点にとどまる。この制約を承知した上で実施し、
レビュー結果を過信しない。ベンダーを跨いだ検証が必要な高リスク変更は、Claude Codeが
利用できる環境で層3を実施する。

## 承認境界

### 自律実行できること

- リポジトリ、コード、設定、履歴、Issue、PR、ログの読み取りと調査
- 診断、設計案、実装計画、テスト計画、レビュー結果の作成
- 承認済み実装に必要な非破壊的なテストと検証

### 事前承認が必要なこと

- コード、テスト、設定、依存関係、DB schemaの変更
- 計画に明記されていないブランチ・worktreeの作成
- 破壊的または本番データへ影響するコマンド
- 依存関係の大規模更新、マイグレーション、本番反映
- commit、merge、rebase、cherry-pick、push、PR作成・更新・レビュー送信
- worktreeの削除

承認済み計画の範囲を超える変更は、追加承認を得るまで実行しない。リモート側では
branch protectionまたはrulesetで`main`への直接pushを禁止し、PR経由を必須にする。
