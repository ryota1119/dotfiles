# X Trend Digest — Xトレンド深掘りレポートスキル

X（旧Twitter）のトレンド／ニュース／特定投稿を起点に、**一次ソースを実際に確認してから**
深掘りレポートを出力するスキル。やり取りはすべて日本語。

このスキルの価値は「Xの投稿をそのまま貼る」ことではなく、**話題の裏にある事実を一次ソースで
検証し、背景と示唆まで含めて構造化する**ことにある。X上の情報は速いが不正確・断片的なので、
必ず元記事・公式発表にあたって「何が事実で、何が憶測か」を切り分ける。

## 全体の流れ

```
Step 0  地域・カテゴリを提示 → ユーザーに選ばせる（固定カテゴリ ＋ 今のトレンド両方）
Step 1  収集（Sonnetサブエージェントに委譲）: ニュース・投稿を集める
Step 2  深掘り・一次ソース確認（同サブエージェント内で必須）: 元記事をWebFetchで検証
Step 3  レポート出力（メインが整形して提示）
```

収集と深掘り（大量のニュース・投稿の読み込みと URL 検証）は **Sonnet のサブエージェントに
委譲**する。理由は2つ:（1）大量の取得・読み込みを安価・高速にこなせる、（2）メイン（あなた）は
ユーザーとの対話とレポート整形に集中できる。メインは Step 0 の対話と Step 3 の整形を担当する。

### 使えるツールの前提（重要）

現在の X MCP は **OAuth 2.0 User Context**（アカウント接続）で動いている。この認証モードでは
使えるエンドポイントに制約がある。**実測で確認済みの前提**は以下:

| ツール | 状態 | 扱い |
|---|---|---|
| `search_news` / `get_news` | ✅ 使える | **主軸**。ニュース収集はこれで行う |
| `WebFetch` | ✅ 使える | **主軸**。一次ソース確認の要 |
| `get_posts_by_id` | ✅ 使える見込み（User Context対応） | 特定投稿の指定があれば使う |
| `search_posts_all` | ❌ 403（App-only認証専用） | **User Context では使えない**。呼んでよいが失敗したら黙って飛ばす |
| `get_trends_by_woeid` | ⚠️ 503 になることがある | 呼んでよいが失敗したら固定カテゴリで代替 |

**設計の芯**: 収集ソースが投稿検索に依存しない。**「ニュース収集 + 一次ソースの WebFetch 検証」だけで
レポートが成立する**ように組む。投稿検索・トレンド取得は「使えれば足す」フォールバック扱いにし、
403/503 が返っても**エラーで止めずに続行**する。将来 App-only Bearer 接続が追加されれば投稿検索も
自動的に活きる。

## Step 0 — 地域・カテゴリの提示と選択

**まず地域のトレンドを取得してから**、固定カテゴリと今のトレンドを一緒に提示する。
ユーザーが具体的トピックや X/Twitter の URL を最初から指定している場合は、この Step を飛ばして
Step 1 へ進む（何を調べるかが既に決まっているため）。

1. `mcp__xapi__get_trends_by_woeid` を **日本（woeid: 23424856）** と **グローバル（woeid: 1）**
   の両方で呼ぶ（`max_trends: 15` 程度）。取得できたトレンド名を候補として使う。
   - トレンド取得が失敗・空でも止まらない。固定カテゴリだけ提示して続行する。
2. 以下を **番号付きリスト** で提示し、ユーザーに番号で選ばせる:

   **A. 固定カテゴリ**（横断的に調べたいとき）
   1. テック / AI
   2. ビジネス・経済
   3. 政治・社会
   4. エンタメ・カルチャー
   5. スポーツ
   6. 科学・学術

   **B. 今のトレンド**（日本＋グローバルで取得した実際のトレンドを番号付きで列挙）
   - 日本のトレンド上位・グローバルのトレンド上位を分けて見せる。
   - Xのハッシュタグ的なノイズ（単なるスラング・ファンダム名など）は省いてよい。

   **C. 最近のブックマークから深掘り**（`get_users_bookmarks` で取得）
   - あなた（篠原さん）が保存した投稿を起点にする。**一次ソース＝公式ドキュメントまで確実に辿れる**ため、
     深掘りの精度が最も高い。直近のブックマークを取得し、要旨を番号付きで見せて「どれを深掘るか」選ばせる。

   **D. 自由入力**（「調べたいキーワードや X の URL を直接どうぞ」）

3. 選択後、必要なら「日本中心 / グローバル中心 / 両方」の軸を軽く確認する（既定は両方）。
   選択が明確なら聞かずに進めてよい。

### 起点の使い分け（重要）

| 起点 | 収集ツール | 一次ソースの追いやすさ | 向く場面 |
|---|---|---|---|
| カテゴリ／トレンド | `search_news` | やや遠い（ニュース経由で公式まで辿る） | 話題を横断で広く拾いたい |
| **ブックマーク** | `get_users_bookmarks` | **確実**（保存済み投稿→公式へ直行） | 気になって保存した話題を深掘る |

全文投稿検索（`search_posts_all`）が現在使えないぶん、**「これを深掘りたい」が明確なときはブックマーク起点が
第一候補**。漠然と「今の話題」を知りたいときはカテゴリ／ニュース起点、と使い分ける。

## Step 1 & 2 — 収集と深掘り（Sonnet サブエージェントに委譲）

選択されたトピックが決まったら、**`general-purpose` サブエージェントを `model: "sonnet"` で1体起動**し、
収集・一次ソース確認・整理までをまとめて任せる。サブエージェントには以下のプロンプトを渡す
（`<トピック>` `<地域方針>` `<特定URL/ID>` を埋める）。

**ブックマーク起点の場合**は、先にメインで `mcp__xapi__get_users_me` を呼んで依頼者のユーザーIDを取得し
（篠原さん＝ @RayOnCode）、プロンプトの「起点」欄に `bookmark（user_id: <取得したID>）` と明記して渡す。

```
あなたはXトレンドの調査アナリストです。以下のトピックについて、Xの投稿・ニュースを収集し、
必ず一次ソースにあたって事実確認したうえで、構造化した調査結果を返してください。

トピック: <トピック>
起点: <category（ニュース収集）/ bookmark（user_id: <ID>）/ post（特定URL/ID）>
地域方針: <日本中心 / グローバル / 両方>
特定の投稿URL/ID（あれば）: <特定URL/ID・なければ「なし」>

## 使うツール（認証モードによる制約に注意）
まず ToolSearch で以下のツールのスキーマを読み込んでから使う。
【主軸＝必ず使う】
- mcp__xapi__search_news      : ニュース検索（query, max_results, max_age_hours）★収集の中心
- mcp__xapi__get_news         : ニュース詳細（id）
- WebFetch                    : 一次ソース（元記事・公式発表）の確認【必須・このスキルの肝】
【起点によって使う】
- mcp__xapi__get_users_bookmarks : ブックマーク起点のとき。id には調査依頼者のユーザーIDを渡す
- mcp__xapi__get_posts_by_id     : 特定投稿の指定があるとき（id, expansions=author_id など）
【フォールバック＝使えれば足す。失敗しても止まらない】
- mcp__xapi__search_posts_all : 投稿検索。※現在の User Context 認証では 403 になる想定。
                                呼んで失敗したら「投稿検索は認証制約で不可」と一言メモして先へ進む。

## 「一次ソース」の定義（このスキルの肝・厳密に守る）
一次ソース ＝ **その事柄の発表元・当事者による公式の一次情報**。具体的には:
- 製品・機能の話 → **提供元ベンダーの公式ドキュメント / リファレンス / リリースノート / changelog / 公式ブログ**
- 企業・組織の発表 → その組織の**公式プレスリリース / IR / 公式アカウントの一次発表**
- 研究・データの話 → **論文本体 / 一次データセット / 公式研究ページ**

ニュース記事・まとめ記事・X投稿は**二次情報**。「Claudeの新機能が出た」という投稿なら、記事で満足せず
**Anthropic公式のドキュメント/リリースノートまで辿って**確認する。二次情報しか無い場合は
「公式一次ソース未確認（二次報道のみ）」と明記する。

## 手順
1. 収集:
   - カテゴリ／トレンド起点 → search_news で20〜40件を集める（クエリは日本語トピックなら "lang:ja"、
     グローバルなら英語キーワードを併用）。
   - ブックマーク起点 → get_users_bookmarks で取得した投稿群を起点にする。
   - 特定投稿の指定 → get_posts_by_id を起点に、その投稿が引用/参照している対象を辿る。
   - 余力があれば search_posts_all も試すが、403 が返ったら黙って飛ばす。
2. 一次ソースの特定: 集めた投稿・ニュースから、話題の核になっている**発表元を特定し、その公式ドキュメント/
   リリースノート/公式発表のURL**を突き止める。記事が貼っているリンクで止めず、記事が参照している
   「元の公式情報」まで遡る。X上の伝聞（「〜らしい」）は一次ソースではない。
3. 事実確認【最重要・必須】: 特定した公式一次ソースのURLを WebFetch で実際に開き、投稿の主張が
   本当にその通りか照合する。最低でも主要な主張3件は公式一次ソースで裏を取る。
   - 公式一次ソースが見つからない／確認できない主張は「公式未確認（二次報道のみ）」と明記する（消さない）。
   - 投稿・記事と公式一次ソースで食い違いがあれば、両方を併記して指摘する。
4. 整理: 以下を切り分けて返す。
   - 事実（一次ソースで確認済み）: 各項目に確認元URLを添える
   - 未確認・憶測（Xでは言われているが裏が取れていない）
   - 背景・文脈（なぜ今話題か、これまでの経緯）
   - 代表的な投稿（エンゲージメントが高い・議論の軸になっているもの数件、URL付き）

## 返す形式（このままの見出しで、Markdownで返す）
### 収集サマリ
- 収集件数 / 期間 / 使ったクエリ
### 事実（一次ソース確認済み）
- 箇条書き。各項目末尾に (確認元: URL)
### 未確認・憶測
- 箇条書き。なぜ未確認か一言添える
### 背景・文脈
### 代表的な投稿
- 投稿の要旨 — @ユーザー / エンゲージメント / URL
### 一次ソース一覧
- タイトル — URL — WebFetchで確認したか（✅/⚠️未確認）
```

サブエージェントが一次ソース確認を省いて返してきた場合（WebFetch のログが無い等）は、
**やり直しを指示する**。このスキルの肝は一次ソース検証なので、ここは妥協しない。

## Step 3 — レポート出力（メインが整形）

サブエージェントの返り値を受け取り、あなた（メイン）が読者＝篠原さん向けに整形して提示する。
**この構成を守る**:

```
# 📊 Xトレンド調査：<トピック>（YYYY-MM-DD）

## TL;DR
- 3行以内で「結局何が起きているか」

## 何が起きているか（一次ソース確認済みの事実）
- 事実を箇条書き。各項目に出典番号 [1] を付ける

## まだ確認できていないこと（憶測・未確認）
- Xでは言われているが裏が取れていない点。なぜ未確認かも書く

## 背景・文脈
- なぜ今話題なのか、これまでの経緯

## 示唆・やるべきこと
- 篠原さん（西日本新聞メディアラボ / DXソリューション部）の仕事・関心への影響
- アクションがあれば「タスク化しますか？」と提案（tasks/ への登録は承認後）

## 一次ソース確認ステータス
| 主張 | 一次ソース | 確認 |
|---|---|---|
| … | [1] | ✅確認 / ⚠️未確認 |

## 出典
1. [タイトル](URL)
2. …
（X投稿は投稿URL、ニュースは元記事URL。一次ソースが無いものは「URL不明」と明記）
```

### 品質のルール
- **一次ソースで裏の取れた事実**と**Xでの憶測**を必ず視覚的に分ける。混ぜない。
- 投稿検索が使えず投稿レベルのデータ（URL・エンゲージメント）が取れなかった場合は、その旨を
  レポート末尾に「調査上の制約」として一言明記する（欠落を隠さない）。「何が起きているか」は
  ニュース＋一次ソース確認で十分に成立するので、投稿が無くてもレポートは完成させる。
- 断定は一次ソースがあるものだけ。無いものは「〜と報じられている」「〜という投稿が多い」に留める。
- 出典URLは必ず記載する。X投稿は投稿URL、ニュースは可能な限り元記事URL。
- レポートは長くしすぎない。TL;DR で結論、詳細は下に。読み手が3分で把握できる密度に。

## 補足

- このスキルは**チャットにレポートを出すのみ**（Vault には保存しない）。ユーザーが「これ取り込んで」と
  言えば、secretary スキルの Obsidian Ingest 手順で `wiki/sources/` に保存する（このスキルの役割外）。
- Xのニュース（Grok 集約）には公開 URL が無い場合がある。その場合は出典に `Grok story ID: <id>` を記す。
- トークン消費が大きい（トレンド取得＋大量収集＋URL検証）。ユーザーが範囲を絞りたい場合は
  収集件数・期間（max_age_hours）を小さくしてよい。
