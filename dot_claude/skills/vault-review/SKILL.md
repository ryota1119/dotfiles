# vault-review — vault の週次検査スタッフ

exocortex vault の現状を検査し、ボスが意思決定できる形に整理する。

**判定は CLI、整理は skill、決定は人間。** 何が問題かは `vaultctl` が決める。この skill は
`vaultctl` の判定を自分で代替したり、独自の基準で「良い／悪い」を判断したりしない
（規約2.1）。何を直すかを選ぶのはボスであって、skill ではない。

やり取りはすべて日本語で行う。

## 役割と他 skill との関係

| skill | 責務 |
| --- | --- |
| `vault-save` | 会話の中身を1ページとして保存する |
| `vault-ingest` | 外部ソースを取り込み、出所を ledger に登録する |
| **`vault-review`** | **既存の vault を検査し、finding を整理して提示する。finding に基づく修正提案はここの責務** |

`vault-review` は新規ページを作らない。既にあるページと ledger の整合だけを見る
（規約2.2）。新しい知識が必要になったら `vault-save` / `vault-ingest` へ渡す。

## 起動と前提

vault のパスは常に明示する。`--vault` は**サブコマンドより前**に置く（規約3.1）。

```bash
vaultctl --vault ~/Workspace/exocortex lint --json --today 2026-08-18
```

**`~/Workspace/exocortex` は Google Drive 上のディレクトリへの symlink であり、git 管理下に
ない。** 書き込みは `vaultctl apply` 経由のみ。`sed -i`・リダイレクト・エディタ・Write/Edit
ツールでの直接編集は禁止（規約6.1）。復旧手段は journal のバックアップと Drive の版履歴
だけなので、疑わしい操作は行わない。

## 検査の手順

1. **`lint --json` を実行する。** `--today <YYYY-MM-DD>` を**必ず明示する**。規則9-b と
   規則10-b は基準日に依存し、省略すると同じ結果を再現できない。終了コードを記録する。
2. **`ledger verify --json` を実行する。** `lint` は規則10を含む全規則を検査し、
   `ledger verify` は同じ検査の部分集合なので追加の finding は出さない。それでも両方を実行する
   理由は、2つの経路が同じ規則10 finding を出すことを照合するためであり、食い違いは ledger の
   検査経路の異常を意味する。出力は lint と形式が違い、`schema` / `counts` のラッパーが無い
   **findings の裸の配列**（規約4.4）なので、同じパーサを使い回さない。
3. **`scripts/review-report.py` に両方を渡す。** `(rule, path, message)` が同じ finding の重複を
   除去して照合結果を報告し、重複除去後の finding を規則番号で4区分へ振り分ける。

   ```bash
   scripts/review-report.py --lint-json <lint.json> --ledger-json <ledger.json>
   ```

4. **区分Dが出ていれば `graph --json` を実行する。** 昇格候補の材料はこちらから取る（下記）。
5. **`references/finding-triage.md` の提示テンプレートに沿ってボスへ提示する。**
   区分Aに入った finding のうち、修正内容が一意に決まらないものは提示の段階でBへ落とす。
   **提案と適用要求を分けて書く。**
6. ボスが「直す」と判断した項目だけを bundle 化し、規約3節の書き込み経路へ入る。

中間ファイルはすべて `~/Workspace/tmp/vaultctl-work/<operation_id>/` に置く。vault の中には
絶対に置かない（規約5節）。`operation_id` の `<op>` は `review`。

## finding の提示

4区分（A: 機械的に直せる違反 / B: 判断が要る違反 / C: 要レビュー・出所 /
D: 要レビュー・成熟度）と優先順位、規則別の対処、提示テンプレートは
**`references/finding-triage.md` を正とする**。

区分内の並びは `lint` の出力順をそのまま使い、**skill は並べ替えない**。
区分Dは毎回**上位3件だけ**を出す。規則9-b が10件を超えたら、毎週の判断対象にせず
「まとめて扱う別タスクを立てる」ことを提案する。

## 昇格待ちキュー（規則9-a）の扱い

**LLM の主観で昇格候補を選ばない。** 明示的なガバナンス層がないと、LLM は訓練分布に沿って
知識を平坦化する。skill は**決定論的に計算できる材料だけを並べ、選定はボスが行う**。

材料は `vaultctl --vault ~/Workspace/exocortex graph --json` が出す5列。

| 列 | 定義 | なぜ材料になるか |
| --- | --- | --- |
| `in_degree` | ハブ5枚と自分自身を除いた被リンク数 | 他の知識から実際に参照されている |
| `out_degree` | 実在ページを指す発リンク数 | 他の知識と接続していて孤立した断片ではない |
| `body_bytes` | frontmatter を除く本文のバイト数 | 書き溜まっている量 |
| `updated` | frontmatter の `updated` | 手が入っている新しさ |
| `status` | `developing` / `evergreen` | 現在地 |

固定ソートは `(in_degree desc, out_degree desc, body_bytes desc, slug asc)`。
**「重要そう」「よく書けている」といった列は作らない。**

書いてよいのは計算結果の記述まで（「このページは被リンク7・本文20KB で22件の中で構造的に
突出している」）。**書いてはいけないのは意味の判断**（「成熟しているので evergreen にすべき」）。

昇格対象の選定はボスだけが行う。ボスが明示的に選定したページはレシピ R9-a に限って bundle 化
でき、`apply` には事前承認が必要である。skill が担う選定前の作業は、引き続き `graph --json` の
材料を並べるところまでとする。

## 修正を適用する場合

**bundle 化してよいのは、修正内容が入力から一意に決まる修正だけ。** 値や文章を新たに
書き起こす修正は、それ自体が LLM の判断であり、この skill が排除しようとしたもの。

名指しで除外する（提案はしてよいが bundle には入れない）:

- 規則1 の必須キー欠落・`title` が空・`status` / `type` の値が不正 — 補う値が一意に決まらない
- 規則1 の未定義キー・type 別に使えないキーの削除 — 一意ではあるが**情報を失う**
- 規則2 の `updated < created` — どちらを直すかが決まらない
- 規則6 の空セクション — 削除するか本文を書くかが決まらない
- 規則11 の末尾改行欠落 — **改行を足しても切断された中身は戻らず、破損が検出できなくなるだけ**
- 規則4・5・8・10 のすべて — D-S2 の対象外

bundle 化してよい修正の判定は **`references/fix-recipes.md` を正とする**。

規則9の昇格は D-S27 による唯一の例外として R9-a を使い、次の4条件をすべて満たす場合だけ
bundle 化する。

1. 選定はボスが行い、skill は `graph --json` の材料を並べるだけとする。
2. `mode=replace` 1件とし、プリフライトで frontmatter の差分キー集合が `{status}` のみで
   あることを確認する。本文がバイト単位で不変であることも確認する。
3. `apply` の前に事前承認を得る。
4. R9-a は他のレシピと同じ bundle に混ぜない。

R3-a（規則3の配置修正）は `create` ＋ `delete` の2 write になる。`delete` を含むため、
規約3.2の2と規約8節の追加承認が必要であり、他のレシピと同じ bundle に混ぜない。

`wiki/index.md` を触る修正では、**追記・削除した行以外がバイト単位で不変**であることを検証し、
その旨を提示に書く。index.md の見出し構造が期待と違ったら、挿入位置を推測せず**停止して報告する**。

適用の経路（bundle → `plan` → 承認 → `apply`）、bundle / plan のスキーマ、承認の提示
フォーマット、プリフライト検証は**規約3節・3.2・4節・6.2 を正とする**。ここでは再記述しない。

適用後は必ず `lint` を再実行し、事前に予測した件数と一致することを確認する。ずれたら
追加の write を発行せず、規約7節の停止規則に入る。

## 失敗時の扱い

**想定と実測がずれたら、次の write を発行せず、状態を報告して止まる。**
「もう一度やれば通るだろう」で再実行しない。事象別の対処は規約7節を正とする。

特に、適用後の `lint` の件数が事前の予測とずれた場合は、追加の write をせずに
`lint --json` の差分を提示して指示を仰ぐ。

## 承認境界

規約8節の `vault-review` 列を継承し、狭める方向にのみ上書きする。

**自律実行してよいこと**

- vault の読み取り・検索
- `lint` / `ledger verify` / `graph` / `recover --dry-run` の実行
- `~/Workspace/tmp/` への中間ファイル・bundle の作成
- `vaultctl plan` の実行（vault を一切変更しないことを実装で確認済み）
- finding の整理・提示・修正案の作成

**事前承認が要ること**

- `vaultctl apply`
- `mode=delete` を含む bundle の apply（**削除対象を1件ずつ列挙して提示する**）
- `vaultctl recover` の実行
- ディレクトリ構成・frontmatter schema・lint 規則の変更
- 会社情報を実名・実値のまま保存する判断
- Backlog / Notion など vault 外への転記

**この skill による上書き（狭める方向）:** 修正内容が一意に決まらない finding は、
承認を求める対象にしない。提案として出し、ボスの選択を待つ。

**D-S27 による例外（広げる方向）:** ボスの明示的な昇格決定に基づく R9-a に限り、D-S2 の
bundle 化対象を規則9へ広げる。これは規約8節の「狭める方向にのみ上書き」に対する明示的な例外である。

## 報告形式

1. **検査範囲** — 実行日時、`--today` の値、vault パス、`vaultctl` のバージョン、終了コード
2. **サマリー** — violation / review の件数と、前回検査からの増減
3. **区分別の指摘** — A → B → C → D の順
4. **提案** — 「機械的に直せるもの（承認1回でまとめて消える）」と「ボスの選択が要るもの」を
   分けて番号付きで提示
5. **承認事項** — 適用を求める場合のみ、規約3.2 のブロックを添える

## 運用ルール

- `~/Workspace/CLAUDE.md` と `exocortex/CLAUDE.md` を継承する。**競合したら、より厳しい
  承認境界を採る。**
- ボスが選択する場面は必ず番号付きリストで示す。丸文字（(1)(2)(3) は可、①②③ は不可）を
  使わない。
- 実行記録は `~/Workspace/tmp/vaultctl-work/` 側にだけ残す。**`wiki/log.md` には書かない**
  （週次検査が読み取り専用であるという性質を保つため）。
- 検査で vault を変更していないことを示すため、読み取り専用で終えた回は
  実行前後の `lint --json` が一致することを確認して報告する。
