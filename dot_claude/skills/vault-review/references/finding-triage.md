# finding のトリアージ表

`vaultctl lint` / `vaultctl ledger verify` が出す finding を、ボスが判断できる4区分へ振り分ける
ための対応表。区分の定義・優先順位・提示テンプレートをここに置き、`SKILL.md` からは参照する。

判定そのものは CLI が行う。この表は**判定結果の見せ方**だけを決める。規則の定義を
書き換えたくなったら、この表ではなく `vaultctl` 側（`lint.py` と各 checker）を直す。

---

## 1. 区分の定義

| 区分 | 規則 | 意味 | ボスに求めるもの |
| --- | --- | --- | --- |
| **A. 機械的に直せる違反** | 1・2・3・6・7 | 修正内容が入力から一意に決まりうる。承認1回でまとめて消える | 適用の可否（yes / no） |
| **B. 判断が要る違反** | 4・5・8・11 ＋ A のうち一意に決まらないもの | ページ単位で選択が要る | どのページをどう直すか |
| **C. 要レビュー・出所** | 10-a〜10-d | 知識の信頼性に直結する。放置すると出所が追えないページが残る | 登録するか、ページを落とすか |
| **D. 要レビュー・成熟度** | 9-a・9-b | 「昇格の習慣がない」という構造的課題 | 週に1〜2件だけ昇格を決めるか、見送るか |

**区分Aは規則番号だけで決まる粗い箱である。** A に入った finding のうち実際に bundle 化して
よいのは、`references/fix-recipes.md` の一意性条件を満たすものだけ。満たさないものは提示の
段階で B へ落とす。`scripts/review-report.py` は規則番号でしか分類しないので、この振り分けは
検査手順のステップ5（提示）で人が行う。

**区分マップに無い規則が来たら B に入れ、「未分類の規則 X が N 件」と明示する。**
規則番号は追記のみで振り直されないため、将来 規則12 以降が増えても黙って落とさない。
`review-report.py` はこの警告行を自分で出す。

## 2. 優先順位（固定。恣意性を持たせない）

区分は **A → B → C → D** の順で提示する。理由:

1. A は承認1回で件数が確実に減る。ボスの認知コストが最も小さい。
2. B は violation なので放置すると増え続ける。
3. C は知識の信頼性そのもの。ただし規則10-a は Phase 3 の別タスクなので
   「Phase 3 待ち」と明示して毎回の判断対象から外す。
4. D は緊急性がなく、毎週全件を見ると疲弊する。**毎回 上位3件だけ**を出す
   （`maturity.py` の `PROMOTION_QUEUE_LIMIT = 5` より意図的に少なくしている）。

区分内の並びは `lint` の出力順（`findings.py::sort_findings` による `(rule, path, message)`
昇順）をそのまま使う。**skill は並べ替えない。**

## 3. 規則別の対処表

`level` は `vaultctl` が付ける値。`violation` は規則1〜8・11、`review` は規則9〜10。
**番号の大小と level は対応しない**（番号は追記のみで振り直さないため）。

### 規則1〜3・6・7（区分A の候補）

| 規則 | level | 発火する message | 区分 | 提示に必要な補足情報 |
| --- | --- | --- | --- | --- |
| 1 | violation | `frontmatter を読めません: ...` | **B** | **破損の疑い。最優先で報告する。** ファイルサイズ、末尾バイト、規則11 が同じページに出ていないかを添える |
| 1 | violation | `ファイルを読めません: ...` | **B** | 同上。UnicodeDecodeError なら非原子的追記による切断の典型 |
| 1 | violation | `必須キーがありません: <key>` | B | 欠けているキーと、同 type の他ページでの値の分布。値は創作しない |
| 1 | violation | `title が空です` | B | 本文の先頭見出しを候補として示す（採否はボス） |
| 1 | violation | `tags は文字列リストである必要があります` | B | 現在の値をそのまま示す |
| 1 | violation | `status の値が不正です: X` | B | 許容値の一覧と現在値 |
| 1 | violation | `type の値が不正です: X` | B | 許容値の一覧、現在の配置ディレクトリ（規則3 と連動する） |
| 1 | violation | `type=X では使えないキーです: <key>` | B | **削除すると情報を失う。** キーの現在値を必ず提示に載せる |
| 1 | violation | `未定義のキーです: <key>` | B | 同上 |
| 2 | violation | `<key> の日付形式が不正です: X` / `<key> を日付として解釈できません: X` | **A** | 正規化後の値。元の値から一意に定まる場合のみ A、曖昧なら B |
| 2 | violation | `updated が created より前です` | B | 両方の値。どちらを直すかはボスが決める |
| 3 | violation | `type=X は <dir>/ に置く必要があります` 他 | **A** | 移動元・移動先パス、slug が変わらないこと。**`create` ＋ `delete` の2 write になる** |
| 6 | violation | `見出しだけで本文がない節です: <見出し>` | B | 見出し名と前後の節。削除するか本文を書くかはボスが決める |
| 7 | violation | `wiki/index.md に載っていません` | **A** | ページの `type`（追記先セクションが決まる）と frontmatter の `title`（追記する説明文） |
| 7 | violation | `wiki/index.md に載っているページが存在しません: [[slug]]` | **A** | 該当行の全文 |
| 7 | violation | `wiki/index.md が存在しません` | **B** | **単独の停止事由。** index.md の再生成は vault-review の責務外 |

### 規則4・5・8・11（区分B）

| 規則 | level | 内容 | 提示に必要な補足情報 |
| --- | --- | --- | --- |
| 4 | violation | `リンク先が存在しません: [[slug]]` | リンク元ページ、その行の文脈。**typo なのか未作成ページなのかを区別する材料**として、類似 slug の候補を `vaultctl graph --json` の `slug` 一覧から示す |
| 5 | violation | `どこからもリンクされていません` | そのページの `links`（発リンク先）。**発リンク先が1つでもあれば「相手に1行足すだけ」の候補**なので B-1、無ければ B-2 に分ける（下記4節） |
| 8 | violation | `同期の競合コピーと思われるファイル名です: <name>` | 元ファイルとの差分。**Google Drive 由来の事故なので、消す前に必ず差分を見る** |
| 11 | violation | `末尾が改行で終わっていません` | **破損の疑い。規則1 と同じ最優先枠で報告する。** 末尾数十バイトを16進で示し、文が途中で切れていないかを判断できるようにする。追記途中の切断なら失われた内容は復元できない |

**規則11 は D-S2 の bundle 化許可（規則1〜3・6・7）に含まれない。** 末尾に改行を1バイト足すだけ
という修正自体は一意だが、**切断されたファイルは改行を足しても中身が戻らない**。改行の追加は
破損を検出不能にするだけなので、原因（どこで切れたか）を確認してからボスが判断する。

### 規則9（区分D）

| 規則 | level | 内容 | 提示に必要な補足情報 |
| --- | --- | --- | --- |
| 9-a | review | `昇格待ちキュー: type=X developing=N evergreen=M (developing率 P%)` | type ごとのサマリ表。1行1 type |
| 9-a | review | `昇格待ち: developing のまま更新が古い（type=X, updated=...）` | `vaultctl graph --json` の `in_degree` / `out_degree` / `body_bytes` / `updated` / `status` の5列。**上位3件だけ** |
| 9-b | review | `長期滞留: developing のまま90日以上更新なし` | 経過日数。**10件を超えたら「まとめて扱う別タスクを立てる」ことを提案する**（毎週の判断対象にしない） |

昇格そのもの（`status: developing` → `evergreen`）は **vault-review の bundle 化対象外**。
材料を並べるところまでが責務で、選定はボスが行う。

### 規則10（区分C）

規則10は `lint` と `ledger verify` の両方から出るため、`(rule, path, message)` が同じ finding は
`review-report.py` の照合時に重複除去する。食い違いは重複扱いせず、全件を警告として提示する。

| 規則 | level | 内容 | 区分 | 提示に必要な補足情報 |
| --- | --- | --- | --- | --- |
| 10-a | review | `ledger が参照するページが存在しない（source_id=...）` | C | **Phase 3 待ち。** 件数だけ出し、毎回の判断対象から外す |
| 10-a | review | `source-ledger から参照されていない source ページ（出所が追えない）` | C | 同上 |
| 10-b | review | `refresh_due` 到来 | C | `refresh_due` の日付と経過日数。再取得するか期日を延ばすか |
| 10-c | review | `review_status: unreviewed のまま滞留している（source_id=...）` | C | ページパスと `source_id`。**裏取りするか reviewed にするかの二択**として出す |
| 10-d | review | `claim_ids の X が claim-ledger に存在しない` | C | ページと claim_id |
| 10-d | review | `孤児 claim: X に location.path がない` / `... の location.path が存在しない` | C | claim の `text`（匿名化ルールに注意）と ledger 上の位置 |

## 4. 規則5（孤立ページ）の下位分類

規則5 は件数が最も多く、そのまま並べても判断できない。**発リンクの有無で2つに割る。**

- **B-1: 発リンク先を持つもの** — そのページが既にリンクしている相手に `[[自分]]` を1行足せば
  規則5 が消える。意味的な関係は既に本文で張られているので、**新しい関係を LLM が創作する
  ことにならない**。孤立ページごとに「既にリンクしている相手」の一覧を表で出す。
- **B-2: 発リンクを1本も持たないもの** — 繋ぎ先が構造から決まらない。ボスが「どの concept に
  繋ぐか」または「落とすか」を決める。パスの箇条書きだけを出し、繋ぎ先を提案しない。

判定材料は `vaultctl graph --json` の `links`（実在ページを指す発リンク）。
**`wiki/index.md` に載せることは規則5 の解消にならない**（`check_orphans` はハブ5枚からの
リンクを被リンクに数えない）。index.md への追記を B-1 の代替として提案しない。

## 5. 提示テンプレート

検査結果はこの形で出す。件数が0の区分も見出しを省略せず `— 0件` と書く。

````markdown
## vault-review 検査結果

vault: ~/Workspace/exocortex  (vault_id=exocortex-922705be5d10)
実行: <YYYY-MM-DD HH:MM> / --today <YYYY-MM-DD>
lint exit=<N> / ledger verify exit=<N>

violation <N> 件 / review <M> 件（合計<N+M>件）<前回比があれば併記>

### A. 機械的に直せる違反 — <N>件

| # | 規則 | ページ | 修正内容 | レシピ |
| - | --- | --- | --- | --- |
| 1 | 7 | sources/xxx | wiki/index.md の ## Sources 末尾に `- [[xxx]] — <title>` を追記 | R7-a |

### B. 判断が要る違反 — <N>件

**B-1. 発リンク先から相互リンクを張れば解消するもの — <N>件**

| # | 孤立しているページ | 既にリンクしている相手（この中の1枚に被リンクを足す） |
| - | --- | --- |

**B-2. 発リンクを1本も持たないもの — <N>件**

- <path>

### C. 要レビュー・出所 — <N>件

**C-1. 規則10-a — <N>件 → Phase 3 待ち（今回は判断不要）**

**C-2. 規則10-c: review_status が unreviewed のまま — <N>件 → 判断が要る**

| # | ページ | source_id |
| - | --- | --- |

### D. 要レビュー・成熟度 — <N>件（上位3件のみ提示）

規則9-a サマリ:

| type | developing | evergreen | developing率 |
| --- | --- | --- | --- |

昇格候補の材料（`vaultctl graph --json`、固定ソート `(in_degree desc, out_degree desc, body_bytes desc, slug asc)`）:

| in | out | bytes | updated | slug |
| --: | --: | --: | --- | --- |

### 次に決めてほしいこと

1. <選択肢を番号付きで。区分ごとに1〜2問まで>
````

**提案と適用要求を分けて書く。** 上記は提案。実際に write を伴う適用を求める場合は、
`SKILL.md` の「修正を適用する場合」の節に従い、規約3.2 の承認ブロックを別に添える。

## 6. この表が触れていないこと

- bundle / plan のスキーマ、`operation_id` の命名、中間ファイルの置き場所 → 規約4節・5節
- 修正が一意に決まるかどうかの判定基準 → `references/fix-recipes.md`
- 承認境界 → 規約8節と `SKILL.md`
- 件数がずれたときの停止規則 → 規約7節
